Portable Self-Hosted VPN Router

A Raspberry Pi + cloud VPN system that protects my traffic on untrusted Wi-Fi and onboards my friends in two minutes.

WireGuard tunnel with iptables kill switch, AdGuard Home for DNS-level ad/tracker blocking, and a self-written Python invite portal. Pivoted mid-build from a dual-radio router to a phone-bridge architecture when the Pi Zero 2 W's single radio couldn't act as AP and client simultaneously.

secure-pi-router
WireGuard Raspberry Pi Python iptables Oracle Cloud AdGuard
<2 min Onboarding
$0/mo Infra Cost
3 Active Peers

Click the green dot above to expand the full write-up

The Problem

I spend a lot of time on untrusted networks — coffee shops, hotels, university Wi-Fi. On those networks my ISP or the network owner can see every site I visit, trackers follow me across every device I own, a compromised router could intercept my traffic, and my public IP reveals my physical location. Commercial VPN subscriptions are expensive, have questionable privacy policies, and only cover one device at a time — I wanted a single device that would encrypt everything for me and my friends without trusting a stranger's logging policy.

The Process

Original pitch. A dual-interface router on a Raspberry Pi Zero 2 W: wlan0 broadcasts a Wi-Fi hotspot for my devices, wlan1 (USB adapter) connects upstream to the untrusted Wi-Fi, Bluetooth PAN as a fallback. All traffic encrypted through WireGuard.

The pivot. Halfway through setup I hit a hardware wall: the Pi Zero 2 W only has one Wi-Fi radio. It can't reliably operate as an access point and a client simultaneously — the hacks that exist are unstable and throughput is terrible. Instead of abandoning the project, I rewrote the technical spec around the constraint: the phone becomes the Wi-Fi bridge. The phone connects to untrusted Wi-Fi and rebroadcasts it as a hotspot; the Pi joins that hotspot as a client and runs a WireGuard tunnel to a cloud server I control. End-to-end encryption preserved, constraint absorbed.

What I built

  • Cloud (Oracle Cloud Always-Free VM): WireGuard server for all peers, AdGuard Home for DNS-level ad/tracker blocking (works on every client with no per-device install), a Python self-service invite portal I wrote that mints one-time-use onboarding links, and an admin dashboard showing live connected peers, traffic stats, and one-click revocation.
  • On the Pi: WireGuard client with auto-reconnect, an iptables kill switch (if the tunnel drops, all outbound traffic is blocked instead of silently leaking), pre-configured to auto-join my phone's hotspot on boot.
  • For friends: they install the free WireGuard app, open a link I text them, click "Download config." Two minutes, cross-platform (iOS, Android, Windows, macOS, Linux). Each friend gets unique keys — I can revoke any one without disturbing others.

Failures and Roadblocks

  • Bricked the Pi with the wrong script. Edited setup.sh locally on my laptop, then ran git pull && bash setup.sh on the Pi — but I hadn't pushed. The Pi ran the old version, which reconfigured Wi-Fi in a way that killed my SSH session. Had to pull the SD card, re-flash with Raspberry Pi Imager, and start over. Lesson: verify git state on both ends before running setup.
  • Oracle Cloud's hidden firewall rule. Tunnel connected fine, but any real traffic through it timed out. After an hour of debugging I found Oracle's stock Ubuntu ships with a REJECT all rule at the top of the iptables FORWARD chain. My WireGuard rules were being appended after it, so they never matched. Fixed by inserting at position 1. Lesson: rule ordering is load-bearing; always iptables -L -n --line-numbers before blaming your config.
  • SSH key mix-up. Downloaded two different Oracle key pairs while troubleshooting VM creation and got them mixed up. Spent 20 minutes connecting with the wrong one. Lesson: name keys at download time, not later.
  • NetworkManager vs dhcpcd. My initial scripts assumed the Pi used dhcpcd; modern Raspberry Pi OS uses NetworkManager. Rewrote the network setup code against nmcli. Lesson: check what the OS actually uses before trusting a tutorial.

  • Computer Networking & Internetworks: IP routing tables, policy-based routing via fwmark and custom tables, NAT source masquerade, iptables rule ordering in the FORWARD chain, DNS resolver chains.
  • Embedded Systems: running a full Linux VPN stack on a single-core ARM SoC, systemd service dependencies and boot ordering, resource-constrained design.
  • Cloud Computing: provisioning and securing an Oracle Cloud VPS, VCN and security-list ingress rules, automated provisioning via idempotent shell scripts.
  • Systems Programming: Python HTTP server built on stdlib only, bash scripting for idempotent setup, shell-to-Python bridges via subprocess.
  • Distributed Systems: centralized server with distributed clients, per-peer key distribution without a CA, self-service provisioning without admin intervention.

Reflection & What's Next

The pivot from Mode A to Mode B was the turning point. Instead of stopping when I hit a hardware limitation, I rewrote the technical spec, talked it through with mentors (human and AI), and ended up with a better system than my original pitch. The networking and security topics that felt abstract in class — iptables chains, NAT traversal, public-key cryptography — all became concrete the moment they stopped working. Every debugging session was a concentrated lesson.

This confirmed my interest in the Cybersecurity and Computer Networking threads, and I want to take further coursework in applied cryptography and network security. Next steps: pick up a USB Wi-Fi adapter (Realtek RTL8188 / RT5370) from the ECE Senior Design Lab to restore the original dual-radio design, add HTTPS on the invite portal via Caddy + Let's Encrypt, integrate more aggressive AdGuard blocklists (EasyList, OISD), and build a WireGuard dashboard with usage graphs over time.

Cow GPS Tracker

An ESP32-based livestock GPS collar that classifies cow behavior and reports to a real-time web dashboard over a sub-GHz radio link — a fraction of the cost of commercial collars.

Low-cost livestock GPS tracking system using ESP32-C6 microcontrollers and 915 MHz FSK radio. A collar reads GPS and accelerometer data to classify cow behavior (resting, grazing, walking, running), transmitting to a gateway that feeds a real-time Flask dashboard with live mapping, geofencing alerts, and herd statistics.

ESP-IDF Embedded C LoRa/FSK Flask

Click the green dot above to expand the full write-up

The Problem

Commercial livestock tracking collars cost $150–300 per animal with monthly subscription fees, putting them out of reach for smallholder farmers who still need to know where their herd is, whether an animal has wandered beyond a pasture boundary, and whether any are injured or in distress. For small grazing operations in rural areas there's usually no cellular coverage either, so "just use a pet tracker" isn't an answer.

The Process

Original pitch. A low-cost, battery-powered collar that reads GPS and accelerometer data locally, classifies behavior on-device, and transmits over a long-range sub-GHz radio back to a farm gateway — no cellular, no subscription. The gateway uploads to a Flask dashboard with live mapping and geofence alerts.

What I built

  • Collar: ESP32-C6 + GPS module + accelerometer, powered by an 18650 cell. Firmware in ESP-IDF / embedded C. On-device behavior classifier runs on accelerometer window features — no ML runtime needed on the MCU.
  • Radio link: 915 MHz FSK transceiver; packets are fixed-size with CRC, collar transmits on a duty cycle to preserve battery.
  • Gateway: Second ESP32 with the same radio, USB-connected to a Flask server. Server decodes packets, writes to SQLite, and serves a Leaflet map of live positions with geofence polygons and behavior-colored pins.
  • Dashboard: Real-time updates via server-sent events, per-animal history, geofence breach alerts.

Architecture

    │  915 MHz FSK (fixed-size + CRC)
    ▼
Gateway (ESP32 + radio, USB-tethered)
    │  serial frames
    ▼
Flask server (SQLite + Leaflet map)
    │  SSE for live updates
    ▼

Successes

FeatureOutcome
Per-collar cost~$22 in parts vs. $150+ commercial
Range~400 m line-of-sight with whip antenna
Behavior classes4 classes using window statistics, no ML on MCU
Battery~5 days on an 18650 at 1-min duty cycle
DashboardLive mapping + geofence alerts in-browser

Failures and Roadblocks

  • GPS cold-start battery drain. First prototype re-acquired a fresh GPS fix every wake cycle and burned the battery in under a day. Fixed by persisting ephemeris data across deep sleeps in RTC memory and widening the fix window.
  • FSK packet loss at range. Initial radio config had a wide deviation and high baud rate; packets above ~100 m dropped. Dropping to 4.8 kbps with narrower deviation pushed usable range past 400 m.
  • Accelerometer orientation drift. Classifier assumed the collar sat upright; in practice it rotates freely on the animal's neck. Switched to magnitude-of-acceleration features that are invariant to axis orientation.

ECE Skills Gained

  • Embedded Systems: ESP-IDF, FreeRTOS task model, ESP32 deep-sleep with RTC memory for state persistence, I²C and UART peripheral integration.
  • RF / Communications: 915 MHz ISM band, FSK modulation parameters (deviation / baud / preamble), antenna matching, packet framing with CRC.
  • Signal Processing: accelerometer window statistics (variance, magnitude) for classification without a full ML model on a constrained MCU.
  • Web Systems: Flask + SQLite backend, server-sent events for live push, Leaflet mapping with polygon geofences.
  • Power Engineering: battery budgeting, duty-cycle design to hit multi-day runtime.

Reflection & What's Next

Building the collar end-to-end — chip to browser — showed me how different every layer of the stack looks from the others, and how much of embedded work is really about the trade between power and responsiveness. Confirmed my interest in the Embedded Systems and IoT threads. Next: migrate from raw FSK to LoRa for longer range, add an ML-based behavior classifier on-device now that ESP32-S3 has a vector instruction set, and scale to a multi-animal herd test.

The Problem

A friend had a PC he declared dead after the motherboard stopped posting; I wanted a self-hosted media server with voice control, automated content acquisition, and remote access without opening holes in my home firewall — and he was about to throw the hardware away.

The Process

Hardware recovery. Probed the motherboard, found a blown electrolytic capacitor near the VRMs, replaced it with a matching part, and swapped the CPU (the original had bent pins from mishandling). The board posted on the first try; the GPU turned out to be fine.

The Problem

BestBrains, the tutoring center I taught at, was running scheduling through a spreadsheet and a constant stream of texts between the director, tutors, and parents — missed sessions, double-bookings, and no audit trail. Commercial booking platforms were either too expensive for a small center or didn't cleanly model "parent books for child with a specific tutor at a specific location."

The Process

Domain modeling. Four roles — admin, tutor, parent, student — each with distinct views. Admins manage schedules and users; tutors see their roster; parents book and see their children's sessions; students get a read-only view.

Custom auth. An Active-Directory-style role + permission graph (groups and ACLs in spirit) so I can grant granular permissions without hard-coding role checks everywhere in the controller layer.

Stack. Node.js + Express with server-rendered views and a small amount of client-side JS for the calendar. MongoDB for flexible document storage (student profiles, tutor availability, bookings). Deployed as Docker containers with nginx as reverse proxy for TLS termination.

An AI-augmented test-driven-development runner that generates test cases from prompts and runtime errors, keeping AI-touched code stable across revisions.

Autonomous test generation system that creates and executes test cases from prompts and runtime errors. Full TDD workflow with structured LLM output, sandboxed execution, and a feedback loop from failing tests back to the generator.

Python AI TDD Cursor
300+ Test Cases

Click the green dot above to expand the full write-up

The Problem

When I use an AI coding assistant to refactor or extend code, regressions are easy to introduce and hard to catch — especially in Python, where runtime errors can hide behind type-lax code that the type checker never sees. I wanted a system that would automatically write tests for any module I touched with AI, so every suggestion had a safety net and TDD-style discipline didn't require me to write every test by hand.

The Process

  • Input channels: a prompt ("test the behavior of function X"), a runtime error stack trace, or a diff from an AI-assisted change.
  • Generation: a structured LLM call (with a strict JSON schema) produces a test-case plan — name, setup, inputs, expected outputs or error types.
  • Execution: tests run in a sandboxed subprocess; pass/fail plus coverage are collected.
  • Iteration: on failure, the failing assertion and the original source are fed back into the generator for a refined test (or a bug hypothesis), closing the TDD loop.
  • Integration: a Cursor extension surfaces generated tests inline so I can review before committing.

      ▼
 Test plan (JSON schema)
      │
      ▼
 pytest runner (sandbox)
      │
      ▼
 Pass/fail + coverage ──► IDE
      │
      └─ regression? feed back to LLM ──┐
                                        │
                                        ▼
                                   refined test

Successes

FeatureOutcome
Generated test cases300+ across personal projects
Regression catchesCaught breakages in AI-assisted refactors before commit
TDD disciplineMaintained without writing every test by hand
Structured outputNo free-form LLM responses to regex-parse

Failures and Roadblocks

  • Hallucinated imports. Early versions imported modules that didn't exist in the project and failed at import time. Fixed by passing the actual pyproject.toml / requirements.txt into the prompt as context.
  • Flaky floating-point assertions. The LLM generated strict equality checks for np.pi * 2-style computations; tests passed locally but failed on different Python versions. Moved to pytest.approx in the plan schema.
  • Runaway test suites. One early run generated 80 permutation tests for a 5-parameter function and timed out CI. Capped at 10 tests per function and added a "smoke / extended" tier.

ECE Skills Gained

  • Applied ML / LLM Tooling: structured output (JSON schema) to tame generative text, prompt engineering with project context injection.
  • Testing Systems: pytest internals, subprocess sandboxing, coverage instrumentation.
  • Software Engineering Discipline: TDD workflow, regression boundaries, judging when to trust AI output and when not to.

Reflection & What's Next

The takeaway isn't that AI can write tests — it's that AI output is only useful when constrained by a schema and validated at a real runtime. That pattern (generate → validate → feed back) has shown up in every good AI-assisted tool I've built since. Next: coverage-guided test selection (prefer tests that hit uncovered branches), property-based test generation with Hypothesis, and mutation testing to measure the suite's actual fault detection.
